### Round 3: No-Timeout Steel-Man Analysis

**File:** `noble-six-adr9-no-timeout-analysis.md`  
**Status:** ✅ Merged into ADR-9

Aaron's challenge: "What if we do no-timeout? We just wait indefinitely?" This analysis explores the strongest case for indefinite wait:

**Steel-man for indefinite wait:**
- Timeout is a lie about intent (system denies without human decision)
- System is built to wait (async Promise has no deadline concept)
- Timeout-tuning is proxy for uncertainty (25s → 30s → 60s → 120s: not convergence)
- SSH agent waits indefinitely (precedent in systems design)
- Aaron's usage pattern is async (multitasking, checking Telegram when available)

**Concrete failure mode analysis:**
- `permissionCallback` semantics: indefinite wait is valid (Promise-based, no deadline concept)
- What blocks during wait: in-flight tool invocation, not session/daemon/pipe
- ADR-6 reconnect: `session.disconnected` fires → AbortSignal fires → prompt cancels within one event loop turn ✅
- ADR-7 heartbeat: fully functional during indefinite wait (independent 30s ping, no interference)
- Resource leaks: none — `pendingByRequestId` entry is negligible (64 bytes per pending prompt)
- "Friday → Monday" case: daemon holds entry, heartbeat maintains session, Telegram buttons work 72 hours later, tool executes when tapped

**Recommendation change:** From Q4→120s to **Q4→no-timeout (Branch A).**

### Round 4: Carter SDK Verification (External Agent)

**File:** `carter-sdk-permission-timeout-verification.md`  
**Status:** ✅ Merged into ADR-9

Carter verifies: SDK has NO internal timeout on `onPermissionRequest`. Evidence:

**Implication:** Branch A (no-timeout) is safe end-to-end. No SDK ceiling to honor.
